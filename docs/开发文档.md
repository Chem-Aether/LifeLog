# LifeLog 开发指南

本文说明服务边界、开发环境、启动组合和数据初始化风险。具体接口字段仍以各服务代码及 `/docs` 为准。

## 架构与权责

LifeLog 是单仓库、多独立进程。各后端可独立开发、启动、部署；同属一个仓库不代表它们必须一起运行。

| 模块 | 权责 | 持有的数据 | 默认端口 |
| --- | --- | --- | ---: |
| `font/` | Vue 3 前端、页面状态和交互 | 浏览器本地偏好等 | 5173 |
| `auth` | 注册、登录、验证码、JWT 签发 | PostgreSQL `auth` | 8081 |
| `bill` | 账户、分类、流水、账单统计 | PostgreSQL `bill` | 8083 |
| `travel` | 航班、铁路行程、途经站、足迹 | PostgreSQL/PostGIS `travel` | 8084 |
| `diary` | 日记业务边界；当前仅状态接口 | PostgreSQL `diary` | 8085 |
| `mapserver` | 瓦片、地理编码、行政区、POI、机场和铁路空间数据 | PMTiles、GeoPackage 文件 | 8765 |
| `spyderserver` | 在线查询 12306 车次信息 | 无业务数据库 | 8082 |

`javaserver/` 是 Maven 聚合目录；`common` 是供 Java 服务引用的基础库，不是服务，也不拥有业务表。Java 服务各自拥有数据库和迁移/初始化脚本，不应跨库读写。认证服务签发 JWT，Java 业务服务通过 `common` 本地验签，不需要在每个请求时调用认证服务。账单和旅行数据不以 `user_id` 关联用户；日记模块尚未完成，其当前占位表仍包含 `user_id` 字段，后续实现前应先确认是否保留。

### 服务调用关系

- 前端分别请求账单、旅行、认证、地图等接口，服务地址由 `font/.env` 中的 `VITE_*_BASE_URL` 设置。
- `travel` 调用 `mapserver` 获取空间和地理能力；因此需要路线/地理相关功能时启动 mapserver。
- 仅在线自动查询车次时，`travel` 才需要 `spyderserver`。手工管理行程、按本地空间数据检索不依赖爬虫。
- 媒体上传由日记/旅行 Java 服务接收并写入 SeaweedFS S3；业务库仅保存对象相对路径。前端通过 `font/.env` 中的 `VITE_MEDIA_BASE_URL` 配置访问地址，Java 服务的 `SEAWEED_S3_ENDPOINT` 只用于上传和删除对象。
- 账单服务不依赖旅行、地图、媒体或爬虫服务。

## 环境准备与启动

需要 Node.js/npm、JDK 21、系统 Maven、PostgreSQL；旅行数据库还需要 PostGIS。仓库未附 Maven Wrapper。Python 服务按各自 `requirements.txt` 建立环境。具体版本以模块配置为准。

### 前端

```powershell
cd font
npm install
npm run dev
```

本地服务 URL 配置在 `font/.env`，包括 `VITE_AUTH_BASE_URL`、`VITE_BILL_BASE_URL`、`VITE_TRAVEL_BASE_URL`、`VITE_DIARY_BASE_URL` 和 `VITE_MAP_BASE_URL`。服务未启用时，应在前端配置中关闭或避开对应功能。

### 单独启动 Java 服务

在 IDEA 中导入 `javaserver/pom.xml`，运行所需服务的启动类；也可在 IDEA 的 Maven 工具窗口对具体模块运行 `spring-boot:run`。常用入口：

| 服务 | 启动类 | 数据库 |
| --- | --- | --- |
| 认证 | `com.lifelog.auth.AuthServiceApplication` | `auth` |
| 账单 | `com.lifelog.bill.BillServiceApplication` | `bill` |
| 旅行 | `com.lifelog.travel.TravelServiceApplication` | `travel` |
| 日记 | `com.lifelog.diary.DiaryServiceApplication` | `diary` |

服务配置分别位于各自 `src/main/resources/application.yml`。常用连接环境变量：`AUTH_DB_URL`/`AUTH_DB_USERNAME`/`AUTH_DB_PASSWORD`、`BILL_DB_URL`/`BILL_DB_USERNAME`/`BILL_DB_PASSWORD`、`TRAVEL_DB_URL`/`TRAVEL_DB_USERNAME`/`TRAVEL_DB_PASSWORD`、`DIARY_DB_URL`/`DIARY_DB_USERNAME`/`DIARY_DB_PASSWORD`；具体变量名以对应配置文件为准。不要把真实密码提交到 Git。

### 单独启动 Python 服务

在对应服务目录使用其 Python 环境执行 `python main.py`。默认端口为：mapserver 8765、spyderserver 8082。媒体文件存储依赖 SeaweedFS S3（默认端口 8333），不再启动独立媒体服务。依赖安装、数据路径和环境变量见各自 README。FastAPI 服务通常在 `/docs` 提供接口文档。

## 数据库初始化与数据安全

数据库名称与模块一一对应：`auth`、`bill`、`travel`、`diary`。初始化前先阅读并检查目标脚本和连接配置，确认目标主机、数据库名称及备份；脚本使用的数据库账户应仅拥有必要权限。

**统一初始化约定：数据库创建脚本只负责建库，不删除已存在数据库；服务启动时执行该模块当前 schema。日记 schema 会清理早期占位表中的 `user_id`，不在日记业务表引入多用户字段。**

| 服务 | 脚本 | 行为提醒 |
| --- | --- | --- |
| 认证 | `javaserver/auth/database/init.sql` | 仅在数据库不存在时创建 `auth`；启动时执行 `schema.sql`。 |
| 账单 | `javaserver/bill/database/init.sql` | 仅在数据库不存在时创建 `bill`；启动时执行当前 `schema.sql` 和基础分类初始化。 |
| 旅行 | `javaserver/travel/database/init.sql` | 仅在数据库不存在时创建 `travel`；启动时执行 PostGIS schema。 |
| 日记 | `javaserver/diary/database/init.sql` | 仅在数据库不存在时创建 `diary`；启动时执行 `schema.sql`。 |

首次创建数据库时，在 LifeLog 根目录使用 `psql` 运行对应脚本，例如：

```powershell
psql -v ON_ERROR_STOP=1 -U postgres -d postgres -f javaserver/auth/database/init.sql
psql -v ON_ERROR_STOP=1 -U postgres -d postgres -f javaserver/bill/database/init.sql
psql -v ON_ERROR_STOP=1 -U postgres -d postgres -f javaserver/travel/database/init.sql
psql -v ON_ERROR_STOP=1 -U postgres -d postgres -f javaserver/diary/database/init.sql
```

这些脚本使用 `psql` 的 `\gexec` 元命令，应通过 `psql -f` 执行，而不是粘贴到普通 SQL 编辑器。数据库已存在时脚本不做任何更改。之后启动对应服务即可创建当前版本的表结构；普通开发启动无需重复运行建库脚本。旧表结构不会被自动转换，结构变更应按项目当前策略明确处理。项目不提供自动清库脚本；确需重置时，应另行确认数据库目标、备份后由管理员执行明确的重建操作。不要清理 GeoPackage、PMTiles、媒体目录或数据库文件，除非确认其可恢复且已备份。

## 数据归属与一致性

- 旅行业务记录归 `travel`；行政区、机场、POI、铁路网络和离线瓦片归 mapserver 管理的独立空间文件。
- 账单账户、分类和流水只归 `bill`。收入/支出/内部转账由账户方向表达，分类仅用于归类和统计。
- 用户凭据只归认证服务。JWT 是服务间验证身份的凭证，不意味着业务库自动具备多用户隔离。
- 图片/视频对象由 SeaweedFS S3 保存；日记和旅行数据库仅保存对象相对路径。SeaweedFS 凭据只配置在 Java 服务端，前端不持有 S3 密钥。
- 日记条目、标签及媒体 URL 关联归 `diary`；足迹媒体 URL 归 `travel`。

## 代码修改原则

1. 业务规则、接口 DTO、数据访问和表结构由所属服务负责。
2. `common` 仅放多个 Java 服务确实共享的稳定基础设施，不放某一业务的实体或规则。
3. 服务间通过 HTTP 接口交互，不直接读取另一个服务的数据库或私有文件目录。
4. 更新配置或接口后，同步更新对应服务 README；涉及数据初始化、删除或迁移时，明确记录备份与恢复步骤。
